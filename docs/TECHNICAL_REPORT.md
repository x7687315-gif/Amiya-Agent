# Amiya Agent 技术报告（2.x 阶段）

> 版本：2026-11-28 · 本仓库为 2.x 后端架构的公开镜像
> 规模：应用代码 13,229 行 · 测试 8,691 行 / 48 文件 · **306 passed**（CI 后端子集）
> 数据模型：SQLite schema **v6**
> 读者：需要了解"怎么做的、为什么这么做、哪里还没做到"的同学与老师。
> 配套：`README.md`（面向快速理解）· `docs/2x/IMPL_*.md`（每个子系统的实施记录）

## 摘要

本项目从一个"能稳定扮演角色的聊天程序"，演进为一个**有行动能力、有记忆、可被验证**的本地智能体。
本阶段的核心工作不是增加功能，而是解决三类系统性问题：

1. **协议层**：与服务端工具（联网）的真实约束对齐——文档没写、只能实测的行为；
2. **检索层**：把"命中了几条"变成"命中的是否相关、失败是否可区分"；
3. **工程层**：让依赖漂移、数据迁移、审批失败这些"不会报错但会出事"的路径可被发现。

我们刻意保留了三组**负结果**（混合检索无收益、知识侧闸门不可行、首版实验无效），
因为它们的价值高于"看起来成功"的指标。

## 1. 背景与目标

### 1.1 起点

Phase 3C 时，Runtime、Tool、Router 已经抽出，但**没有任何真实调用方**：
`internal_task` 信号零调用，任务系统是"装好的机器，没有产品入口"。

### 1.2 阶段目标

| 目标 | 判定标准 |
|---|---|
| 行动系统接上产品面 | 用户能进任务模式、看状态、审批、取消 |
| 联网可用且诚实 | 能搜、能读、有来源；**没调用工具时要明说**，不能假装成功 |
| 检索质量可度量 | 有评测集与阈值数据，不靠"感觉还行" |
| 不破坏既有行为 | 快路径提示词逐字节不变；新能力默认关闭 |

### 1.3 非目标

- 不做多用户/云端部署；
- 不做通用 Agent 框架（不追求支持任意工具生态）；
- 不追求"更自主"，先追求"更可信"。

## 2. 架构：从单体编排到分层

### 2.1 旧结构的问题

`agent.py` 同时承担：检索、提示词拼接、模型调用、落库、情绪更新。
结果是：任何一处改动都要读 400 行；测试只能整体测；无法在不启动 UI 的情况下验证组装逻辑。

### 2.2 新结构

```
ui/            表现层：只发意图、渲染结果，不含业务判断
core/application/  应用层：Facade / Router / Runner / 审批桥
core/agent.py      认知层：检索 → 组装 → 生成 → 落库
core/runtime/      运行时：状态机、事件、Run 仓储
core/tools/        工具层：协议、校验、权限、执行
core/memory, knowledge, persona …  领域层
```

**依赖单向**：`ui → application → agent/runtime → tools → storage`。

### 2.3 三个关键抽出

| 抽出物 | 从哪来 | 为什么 |
|---|---|---|
| `ContextAssembler` | `agent.reply()` 中间 40 行 | 让"组装"可单测、可被任务路径复用；九段顺序有字节级测试 |
| `AgentRuntime` | 新写 | 模型只提议行动，执行与状态在本地；每步落 `agent_run_step` |
| `ResearchRunner` | 新写 | 联网是独立流程（服务端工具、来源、会话），不该塞进聊天主链 |

## 3. 架构决策记录（ADR）

> 每条格式：**问题 → 选项 → 决定 → 代价**。只记录"有争议、有代价"的决策。

### ADR-1 记忆相关性闸门放在"准入"而不是"调阈值"

- **问题**：无关提问也返回满 5 条记忆。
- **选项**：(a) 提高 `min_score`；(b) 调整通道权重；(c) 增加准入闸门。
- **决定**：(c)。数据证明 (a) 无效——所有名次分数都 ≥0.30，`min_score=0.05` 从未生效。
- **代价**：召回下降。「今天好累啊」从 5 条变 0 条（余弦 0.40 < 0.50）。

### ADR-2 检索返回"状态"而不是裸列表

- **问题**：`[]` 同时表示"没有相关内容"与"检索坏了"。
- **选项**：(a) 只在日志里区分；(b) 抛异常；(c) 返回 `RetrievalOutcome`。
- **决定**：(c)。异常会打断对话；日志没人看；状态可以进 metadata、trace 与 UI。
- **代价**：接口变宽，所有调用方要处理 `status`；用 `retrieve()` 薄包装保持兼容。

### ADR-3 研究会话存原始协议 JSON，不解析

- **问题**：多轮联网要回传 `server_tool_calls`（含加密 `signature`）。
- **选项**：(a) 解析成业务字段存表；(b) 原样存 JSON。
- **决定**：(b)。协议字段可能变，解析后再存会随版本漂移；原样存最保守。
- **代价**：无法在库里查询"某个 URL 被读过几次"；需要时再从 JSON 解析。

### ADR-4 真实 API 测试不进 CI

- **问题**：联网协议只能实测，但 CI 需要稳定。
- **选项**：(a) 全进 CI；(b) 全不进；(c) 分层：离线进 CI，真实 API 手动。
- **决定**：(c)。真实 API 花钱、受网络波动影响，进 CI 会让红绿失去意义。
- **代价**：协议回归依赖人记得跑；用 `live_smoke.py` 降低执行成本。

### ADR-5 不引入向量数据库

- **问题**：记忆千级、知识百级，是否需要 FAISS/sqlite-vec？
- **决定**：不引入。候选集暴力余弦，`candidate_limit=500`，实测远低于一次首字延迟。
- **代价**：数据量上万时需要替换；替换点已收敛到 `_vector_scores()` 一个方法。

### ADR-6 混合检索实现但默认关闭

- **问题**：BM25 + RRF 是否值得默认开启？
- **决定**：默认关。评测显示 R@10 +4.2pp、MRR −2.2pp，净收益在噪声内。
- **代价**：代码是"死"的（有测试、有评测、无默认路径）；但保留 jieba 分支，装上即生效。

## 4. 五个关键故障：根因与验证

> 这一节是本报告的核心。每个故障都记录"怎么定位的"——方法比结论更可复用。

### 4.1 联网 400：`an assistant message must follow a user message`

**现象**：🌐 模式一发就问，400；普通聊天正常。

**定位**：只读查库，把最近 40 条消息的 role 列出来——第 36 条是 assistant，
而 `HISTORY_LIMIT=20` 保留 40 条，窗口切在一轮对话中间。

**验证**（真实 API，四组对照）：

| 请求形态 | 首条 | 结果 |
|---|---|---|
| 普通 `chat_with_tools` | assistant | 200 |
| 带 `deepseek_web_search` | assistant | **400** |
| 带服务端工具 | user | 200 |
| 带服务端工具、连续两条 user | user | 200 |

**根因**：服务端工具请求对序列更严格，官方文档未写这条差异。

**修法**：`Agent._window()` 归一化（丢开头非 user、连续 assistant 只留最后、跳过空内容），
`core/protocol_guard.py` 在出站前留痕兜底。

### 4.2 模型不调用联网工具

**现象**：卡片"已完成"但无来源，回答"罗德岛查不到湛江天气"，并编造"源灾浓度"。

**定位**：同句、同模型，只换 system prompt 的三组对照：

| 组 | system | 服务端调用 | 结果 |
|---|---|---|---|
| A | 极简"先搜索再回答" | 1 | 正确 |
| B | 完整人格 | **0** | 拒绝回答 |
| C | 人格 + 联网规则 | 1 | 正确且贴合人设 |

B 组 `usage.server_tool_use = None`，证明请求里根本没有工具执行。

**根因**：人格提示的三条约束叠加（不跳出角色 / 不知道别编造 / 面对面说话），
模型判断"角色设定里不该知道现实世界"，宁可不查也不出戏。

**修法**：`RESEARCH_RULES` 拼在 persona 之后，只对联网路径生效。

### 4.3 向量检索静默失效

**现象**：评测所有指标为 0。

**定位**：直接 `get_embedder("auto").encode(["x"])` → `ImportError: is_offline_mode`。

**根因（两层）**：`transformers 5.14` 要求 `huggingface_hub>=1.5`，实际 0.30.2；
修完又撞 `soundfile` 的 `libsndfile.dll` 缺失。

**影响**：`_embed_all()` 捕获异常返回 `[]` → 知识检索恒为空，记忆向量通道降级。
**这不是展示问题，是整条向量路断了。**

**修法**：绕开不可达的 pip 镜像升级依赖；新增 `embedder.probe()` 真跑一次 encode，
启动时后台探测，失败在聊天区提示。

### 4.4 记忆永远凑满 5 条

**现象**：`参考：5 条记忆`，包括问天气。

**定位**：复制库、取 23 条真实提问、`min_score=0` 跑 top-8，打印分项：

```
1. score=0.406  vec=0.231 kw=0.00 rec=0.92 imp=0.67 | 21岁，生日为11月19日
```

**根因**：`recency/importance/confidence` 是记忆自身属性，给每条记忆垫底分；
它们决定"是否入选"，`top_k` 就永远填满。

**修法**：准入闸门（`vector ≥ 0.50` 或 `keyword ≥ 0.20`），先验只参与排序。
**效果**：184 → 63 条命中；无关查询 0 条，相关查询 4–5 条。

### 4.5 混合检索没有收益（负结果）

**做法**：BM25（标识符正则保护 + 中文分词）+ 向量双路 → RRF，默认关。

**评测**（24 查询 / 152 块）：

| 系统 | R@5 | R@10 | MRR | nDCG@10 |
|---|---|---|---|---|
| dense | 0.750 | 0.750 | 0.646 | 0.672 |
| hybrid | 0.750 | 0.792 | 0.624 | 0.665 |
| BM25-only | 0.667 | 0.667 | 0.548 | 0.576 |

**归因**：① 本机装不上 jieba（19MB sdist 超时），退化 bigram，常见二元组盖过稀有标识符；
② 语料同主题多文档，RRF 把"另一份文档里的同主题块"顶上来，标签算错；
③ BM25 在极小语料 IDF 退化（N=2 时 df=1 的 IDF 恰为 0）。

**决定**：默认关闭，保留 jieba 分支与评测脚本。

### 4.6 研究会话：丢 signature 会静默重搜

**设计前提验证**（三组，详见 `RESEARCH_SESSION_EVIDENCE.md`）：

1. 首版实验**无效**——第 1 轮回答已把答案讲完，B 组靠摘要答对；
2. 收窄第 1 轮 + 工具开启：B 组 `calls=1 / sources=15`，**答案正常但重新搜了**；
3. 关掉工具：A 组能复述 `data=""` / `signature`，B 组"只读到标题，没有正文"。

**结论**：前提成立；且生产环境的真实风险是**成本与来源漂移**，不是答错。

## 5. 数据模型与迁移

### 5.1 表

| 表 | 作用 | 引入版本 |
|---|---|---|
| `conversation` | 对话原文 | v1 |
| `memory` | 长期记忆（含向量、衰减、确认时间） | v1 |
| `memory_candidate` | 抽取候选（待合并/待确认） | v2 |
| `user_profile` | 画像键值 | v1 |
| `persona_state` | 关系/情绪/陪伴时长 | v1 |
| `memory_blacklist` | 不记的内容 | v1 |
| `agent_run` / `agent_run_step` | 任务运行与步骤 | v4 |
| `assistant_task` | 任务与到期提醒水位 | v4 / v5 |
| `research_session` | 联网协议状态 | v6 |

### 5.2 迁移策略

- 逐版本推进，每步 `executescript + PRAGMA user_version` 单独提交；
- 升级前备份，但**仅当库里已有表**（空库不产生垃圾备份）；
- 测试用真实 v1 库验证 v1→v6：行数、字段、每版新增结构。

### 5.3 为什么不用 ORM

表的数量与查询复杂度都在"手写 SQL 更清楚"的范围内；ORM 会隐藏迁移顺序与事务边界，
而这两件事恰恰是数据安全的关键。

## 6. 测试策略

| 层 | 数量 | 是否进 CI | 说明 |
|---|---|---|---|
| 单元 | 主体 | 是 | 纯函数、解析、打分、状态机 |
| 集成 | 中量 | 是 | Agent + 假 LLM + 内存库 |
| UI 组件 | 少量 | 是 | 用桩替换 `ft.Control.update`，无真实窗口 |
| 协议离线 | 7 | 是 | 消息序列校验、窗口归一化 |
| 迁移 | 5 | 是 | v1→v6、幂等、备份、升级后可写 |
| 真实 API | 4 组 | **否** | 手动执行，合成消息，不写库 |

设计取舍：

- **不追求覆盖率数字**，追求"失败路径有断言"。例如嵌入抛异常时代码必须返回 `DEGRADED`，
  而不是空列表。
- **断言要锁行为，不锁实现**。`test_system_prompt_byte_equivalent` 锁的是提示词顺序与用词
  （用户可感知），不是函数调用次数。
- **失败的实验也写测试**。`test_bm25_identifier_beats_filler_text` 里注释了 bigram 的边界，
  防止后来者误以为"BM25 一定能救标识符"。

## 9. 局限

1. **知识侧精度受限于双塔检索**：余弦衡量话题接近，不衡量"能否回答"；
   解决要 cross-encoder，当前未做。
2. **研究会话不跨重启**：内存态 `_active_id`，重启丢连续性。
3. **UI 与后端不同步**：检索状态、会话三态、任务历史都只有后端数据，界面未完整呈现（见 README §16.1）。
4. **语音只有 TTS**：ASR 与全双工未做。
5. **评测集偏小**：24 条检索查询，结论只能做相对比较，不能宣称绝对质量。

## 11. 结语：这一阶段真正学到的东西

1. **"返回成功"不等于"拿到了想要的东西"**。HTTP 200 可以是空回答、丢上下文、静默重搜。
2. **先验属性不能替代相关性**。把"重要"和"相关"混进一个分数，结果就是永远有答案、永远不精准。
3. **降级必须有信号**。凡是"失败后返回空"的路径，都要有状态、有日志、有 UI 提示，
   否则故障会以"正常但没结果"的形态长期潜伏。
4. **负结果要写下来**。混合检索没收益、知识闸门不可行——不写，下一个人会重做一遍。
